# Detection and classification

Inspect manifests, npm lockfile, separate build/runtime workspace graphs, framework configs, source routes, port/listen behavior, iframe response-header restrictions, filesystem writes, database use and versioned framework contracts without executing project code.

## Branches

- `frontend-static`: recognized static build output or reviewed package-free static tree. Frontend fields only.
- `backend-http`: one Node HTTP backend. A hand-written SSR monolith — a single manifest holding both a frontend framework (react/vue/svelte) and a Node HTTP framework (express/koa/fastify/hapi/nestjs) whose resolved production entry or project-local relative import/require closure actually serves the built frontend — is also `backend-http`: one backend component, catch-all `/*`, source entry plus an asset build, never split into `fullstack-split`. Build output strings in client or tool configuration are not serving evidence.
- `ssr-node`: one Node SSR server with a statically proven or Agent-build-verified recipe, artifacts and runtime entry. Versioned static mappings currently include Next, vinext, Nuxt and SvelteKit.
- `fullstack-split`: static frontend plus one Node backend.

Never attach RuntimeManifestMode, RuntimeEntry, RuntimePackagePath, RuntimeLaunch, CloudFunctionRuntime or runtime naming fields to frontend components.

## Manifest mode

Use `root` only when the backend/SSR component directory is `.` and the project is `backend-http` or `ssr-node`. This proves the root manifest owns the runtime component and production dependency declarations.

Use `overlay` for nested Node services, workspace SSR, split full-stack projects, aggregator roots, missing root runtime dependencies, or any ambiguous dependency ownership.

## Backend resolver evidence

Every backend component carries `RuntimeResolution`, ordered `BuildRecipe`, generated-only `BuildArtifacts` and resolver-owned `RuntimeLaunch`. Select one resolver for the actual backend family instead of applying one directory heuristic to every project. The resolver must emit one `output-path` fact and one `runtime-entry` fact, plus the build command fact when a build exists. Each fact records `Source`, normalized `Value`, and `Method`; the validator rejects missing or mismatched evidence. `BuildCommand`, `OutputPath` and legacy workspace order are compatibility projections and cannot disagree with the authoritative recipe/artifacts.

Evidence precedence is: reviewed explicit value with matching BuildValidation, framework/build configuration, production manifest, then a versioned fixed framework contract from `node-framework-contracts.json`. An implicit configurable default is not final evidence. Missing literal configuration emits `E_BACKEND_OUTPUT_CONFIGURATION_REQUIRED`; dynamic or multi-output configuration emits `E_BACKEND_OUTPUT_AMBIGUOUS`. Static framework evidence records the contract ID and exact lockfile version. Dynamic/multi-output config and tools outside the closed resolver set require Agent build; output/entry overrides without matching commands, fresh artifacts and optional HTTP probe evidence are rejected. Local build output remains excluded from delivery.

Automatic backend selection enumerates packages with both a declared production entry and source-level HTTP listen/createServer/serve evidence. Framework dependencies alone are not candidates. Exactly one candidate may be selected automatically; multiple candidates emit `E_MULTIPLE_BACKEND_CANDIDATES` and require `--backend-dir`.

BuildGraph traverses local dependencies, optionalDependencies and devDependencies; RuntimeGraph traverses only dependencies and optionalDependencies. BuildGraph cycles block deterministic ordering. The closed static backend build set is committed Node entry, `tsc -p/--project/--project=`, `tsc -b/--build` with relative extends/references, Nest CLI, version-covered framework resolvers, and a committed Node entry with statically proven Vite assets. Other bundlers, orchestrators, custom shell and dynamic framework configuration require Agent build.

## Entries

Normalize all entries and artifacts from project root and reject absolute paths, traversal and control characters. An unlisted Node framework may be delivered only when its recipe, artifacts and entry are proven statically or by BuildValidation. Ordinary Node entries come from an explicit reviewed value, a simple `node <entry>` start script, or package `main`. When the entry already exists as committed source, a build command may produce separate runtime-read assets and `OutputPath` stays null. For a same-manifest frontend/server monolith, backend source checks follow the resolved entry's project-local relative import/require closure; transitive runtime workspace packages remain fully scanned.

Treat manifest start/main entries and every effective TypeScript `compilerOptions.outDir` as declarations relative to the file that owns them, including a leading `../` that remains inside the project. Resolve `--project=`, build mode, project-local relative extends, project references, Nest `tsConfigPath`, and `tsconfig.build.json`; collect all required referenced outputs and choose the primary output containing RuntimeEntry. Normalize final paths exactly once and never prepend `Directory` again.

Resolve launch behavior once and record it in `RuntimeLaunch`; runtime generation and validation must not reopen `package.json` to choose again. Root framework outputs whose versioned contract declares `LaunchKind: node-entry` run the resolved artifact directly even when a generic framework `scripts.start` exists. Root ordinary Node, Nest and hand-written SSR monoliths preserve a non-empty `scripts.start` as `npm-script`; without one they use `node-entry`. Overlay always selects the generated `npm-script:start`. A new SSR resolver must declare its launch kind explicitly instead of inheriting a blanket SSR rule.

Normalize the Node major in this evidence order: explicit reviewed override, component `.nvmrc`, component `.node-version`, component `package.json#engines.node`, then root `package.json#engines.node`. Carry the same major into the plan and backend descriptor; bootstrap startup selection is independent of the binary version path. Do not replace a detected value with a Skill default. If no single major can be proven, emit `W_NODE_VERSION_FALLBACK` and use the documented compatibility fallback only after the warning is visible.

Derive `CloudFunctionRuntime` separately from the detected major by rounding upward to fixed targets 16, 18, 20, 22 or 24. The corresponding runtime literals are `Nodejs16.13`, `Nodejs18.15`, `Nodejs20.19`, `Nodejs22.21` and `Nodejs24.11`; installDependency is true through target 20 and false above 20. A major above 24 has no automatic mapping and emits `E_CLOUDBASERC_RUNTIME_UNSUPPORTED`. Only an explicitly user-authorized `--backend-cloud-function-node-version 24` may record a reviewed downgrade, without changing `NodeVersion`.

## Blocking findings

Root `cloudbaserc.json` is generated only for backend and SSR branches.

Block Node majors above the fixed cloudbaserc table unless an explicitly reviewed override is present.

Explicit JavaScript frame-busting redirects guarded by `top`/`self` embedding checks are iframe blockers under the same hard gate as CSP and X-Frame-Options.

Block unresolved entries/build tools/outputs, mismatched Agent evidence, out-of-range framework contracts without build verification, workspace build cycles, multiple backend candidates, incompatible SSR configs, incomplete npm conversion/lockfiles, hardcoded ports, loopback-only listeners, unsupported user environment access, effective CSP `frame-ancestors 'none'`/self-only restrictions, `X-Frame-Options: DENY/SAMEORIGIN`, filesystem writes, database/persistent-state dependencies, escaped symlinks, secrets, and multiple runtimes. Runtime source environment checks allow only the variables emitted by the generated bootstrap: `PORT`, `HOST`, `HOSTNAME`, `NITRO_HOST` and `NITRO_PORT`; this allowlist comes from the same deterministic setting consumed by bootstrap generation. Any other named access, destructuring, dynamic bracket access or use of the complete `process.env` object emits `E_USER_ENVIRONMENT_VARIABLE_UNSUPPORTED` with variable names when statically available and source lines. Do not expose internal descriptor fields or attempt to classify names or values as sensitive. Tell the user that remediation places every value in plaintext project source and the ZIP, readable by anyone with access, and ask for explicit authorization to rewrite every match. Clear authorization permits the minimal project-local rewrite in the isolated delivery source; decline, silence or ambiguous consent remains blocked. Do not repeat values in the final handoff. Iframe checks scan effective runtime source plus common checked-in header configuration while excluding tests, fixtures, examples, generated output and comments. `E_IFRAME_EMBEDDING_FORBIDDEN` is a hard packaging gate: do not generate or reuse runtime inputs, descriptors, or an archive while it is present. Removing iframe restrictions changes clickjacking protection and requires explicit user authorization to remove every match. Ask only for that complete authorization; never offer partial removal that retains an effective blocker while continuing packaging. Decline, skip, silence, or ambiguous consent remains blocked. Authorization permits the minimal source/configuration change but does not unlock packaging by itself. Remove every matched directive/header, preserve unrelated CSP and middleware, and re-detect from scratch; artifact generation may resume only from a fresh non-blocked plan where the finding is absent. Port and missing explicit output corrections are mechanical delivery-standard edits and do not require a separate authorization pause. Ambiguous output may be resolved by authorized Agent build/start evidence, never by packaging local artifacts. Do not patch compiled output. Re-detect every source remediation from scratch.
